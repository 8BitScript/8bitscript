# A more modern i18n developer experience

Research notes, not a spec — the same voice as
[`docs/project/machines/index.md`](machines/index.md): every claim below
is cited to a real file, and anything proposed rather than observed is
marked **PROPOSED**. Read the root [`AGENTS.md`](../../AGENTS.md) first;
its "never abstract away a hardware limit" rule governs the character-set
and direction sections below without exception. Written against `trunk`
and the sibling [`2048`](https://github.com/8BitScript/2048) project,
whose catalog files are the real-world case this research is grounded in.

## What exists today — two separate systems sharing the word "locale"

**1. `@8bitscript/i18n` facts** (`packages/i18n/src/index.8bs` plus one
file per locale twin: `index.de.8bs`, `index.fr.8bs`, `index.it.8bs`,
`index.nl.8bs`, `index.pt-br.8bs`). Exposes `Locale.DECIMAL`/
`Locale.GROUP` (the digit-separator characters) and `number.print(...)`.
Resolved by the compiler's ordinary file-twin rule and folds to a
literal — byte-identical to hand-writing the constant
(`packages/i18n/README.md`). This part is small, already clean, and not
what prompted this research.

**2. Message catalogs** — `src/i18n/<locale>.8bs`, imported as
`@8bitscript/i18n/catalog`. This is the actual "language files" the 2048
project ships, and the thing worth redesigning. A catalog is literal
8BitScript source:

```8bs
export namespace Prompt {
    const START: string = "PRESS {control}";
    const START_EITHER: string = "PRESS {control} OR {other}";
}
```

(real example from `2048/src/i18n/en.8bs`, five namespaces — `Game`,
`Prompt`, `Status`, `Hint`, `Copyright` — 17 string keys total, its
German twin `de.8bs` mirroring the same shape.)

The compiler-side contract (`packages/compiler/src/i18n/index.mjs`, 519
lines) is real and non-trivial:

- `discoverCatalogLocales`/`isCatalogFile` find locale-named `.8bs` files
  in a catalog dir (config `i18n.catalog`, or any directory literally
  named `i18n`).
- `catalogSchema` walks the AST and accepts exactly one shape: top-level
  `export namespace X { const Y: string = "..."; }` — anything else is a
  `CATALOG` diagnostic (`index.mjs:238-260`, the `extras` path).
- `compareCatalogSchemas` enforces that every locale exports the same
  `namespace.key` set and the same `{placeholder}` names in the same
  order as the default locale (`CATALOG_SCHEMA`/`CATALOG_PLACEHOLDER`
  diagnostics) — a real, valuable guarantee: a translator can't silently
  drop or rename a `{control}` placeholder.
- `prepareCatalog` merges the selected locale over the fallback per key
  (not per file — a locale can omit individual keys and inherit them),
  then regenerates a synthetic merged `.8bs` module (`emitCatalog`,
  literally re-serializing namespaces/consts as 8BS source text) that the
  rest of the compiler pipeline consumes like any other import.
- `applyCatalogCharset`/`transliterate` run on every string literal:
  `charset: 'transliterate'` (default) maps seven Latin extras (Ä→AE,
  Ö→OE, Ü→UE, ä→ae, ö→oe, ü→ue, ß→SS — `TRANSLITERATIONS`,
  `index.mjs:27-30`) into `CATALOG_CHARACTERS` (the same restrictive
  portable set as everywhere else in the compiler, with `{}` added for
  placeholders); `charset: 'strict'` refuses anything outside that set
  instead of mapping it. Anything not in that seven-entry table and not
  already portable is a hard build error (`UNPORTABLE_CHARACTER`).

**Config shape** (`docs/config.md`, matching the real
`2048/8bitscript.config.ts` exactly):

```ts
i18n: {
  defaultLocale: 'en',
  fallbackLocale: 'en',
  locales: ['en', 'de'],
  charset: 'transliterate', // or 'strict'
},
```

This block itself is small and not obviously ugly in isolation. What's
real is that locale plumbing is spread across three unrelated places in
a real project: this `i18n` block (which locales exist / default /
fallback / charset), each target's `release` array (`{ locale: 'de' }`
entries mixed in with hardware/profile variants — see
`2048/8bitscript.config.ts`'s `pet.release` and `web.release`, where a
locale variant sits in the same list as a hardware-machine variant with
no visual separation), and the ad-hoc `--locale` CLI flag. Three things
answering "what languages does this build in, and how" is the config-side
complaint, more than the `i18n` block's own five lines.

## What's actually ugly, concretely

It's not that the 2048 catalog files are malformed or badly organized —
they're clean, hand-written 8BS. The complaint is structural:

1. **A data file is a programming-language file.** Every string needs
   `export namespace`, `const NAME: string = `, a semicolon, and correct
   8BS string escaping — syntax a translator (who is not an 8BitScript
   engineer) has to get exactly right, in a language they may not know,
   to contribute a translation. A one-character typo (missing `;`, wrong
   quote) is a compiler syntax error, not a friendly validation message.
2. **No standard tooling reads it.** YAML/TOML/JSON/gettext `.po` all
   have mature ecosystems — translation management platforms (Crowdin,
   Lokalise, Weblate), CAT tools, `git diff`-friendly formats, linters. A
   bespoke "8BS with exactly one accepted shape" format has none of
   that; a translator needs a text editor that understands 8BS syntax
   highlighting at minimum, and any tooling integration is custom work
   this project would have to build itself.
3. **The generated-merge artifact is also 8BS** (`emitCatalog`,
   `index.mjs:308-321` — the compiler literally writes out
   `export namespace ${ns} { const ${name}: string = ${quote8bs(value)}; }`
   for the merged catalog it re-parses). This is an internal
   implementation detail today (nothing reads it directly), but it shows
   the whole pipeline is built around "catalog is 8BS source" as a
   load-bearing assumption, not just a surface authoring convenience — a
   format change has to replace the *parser*, not just the file
   extension.

## Character sets — a real, hard constraint, not a gap to fill

`PORTABLE_CHARACTERS` is defined identically in two places
(`packages/compiler/src/checker/index.mjs:67` and
`packages/compiler/src/i18n/index.mjs:19`, `CATALOG_CHARACTERS` adding
only `{}`): space, 0-9, A-Z, a-z, and `! , - . : ?` — 68 characters, full
stop. Every other language-level string literal in the compiler is
checked against this exact set (`checker/index.mjs:73-77`); catalogs get
one extra concession, the seven-entry German transliteration table, and
nothing else. This is deliberate, not an oversight: `packages/i18n/
README.md` states plainly *"Every value is a literal in the portable
character set... so a build never reaches for a glyph its target cannot
draw."* PET/VIC-20/C64/C128/CX16/MEGA65 render PETSCII, Atari 8-bit
ATASCII, NES a fixed CHR-ROM font on NROM (`packages/nes/AGENTS.md`: "no
redefinable glyphs on NROM's CHR-ROM") — none of these is Unicode, none
is even the same 8-bit character ROM as each other, and
`packages/compiler/AGENTS.md` confirms the compiler does not even
convert a string literal to a machine's screen codes at *compile* time
yet — `text.print` does that conversion at **run time**, per character,
from the portable ASCII-ish subset. There is no per-machine compile-time
charset *table* today at all — no "PETSCII", "ATASCII", or "screen code"
table exists as configurable data in the checker/i18n layers; the
mapping lives inside each machine's own `text.8bs`, unexamined in this
pass.

What this means for "non-standard character sets": genuinely expanding
beyond the 68-character portable set (full accented Latin, Greek,
Cyrillic) requires, per machine:

- A redefinable character set (several of these machines' video chips
  support software-defined glyphs — the C64's VIC-II can page in a
  custom charset from RAM; this needs verifying per machine, not
  assumed) **and**
- A build-time mapping from source codepoints to that machine's custom
  glyph table, which does not exist today and would be new compiler
  work, not a catalog-format change.
- On a machine with a genuinely fixed, non-redefinable font (NES's
  NROM, confirmed above), this is not achievable at all without a new
  CHR-ROM/mapper — a hardware-level decision the language cannot paper
  over, exactly the "never abstract away a hardware limit" rule the root
  `AGENTS.md` states as the project's one rule.

**PROPOSED** posture: character-set support should be a per-machine,
per-hardware-value *capability fact* — the same pattern `storage.save`
already sets on the NES's `nrom` mapper value — e.g.
`video.customGlyphs: true/false`, checked by the compiler before a build
claims a codepoint outside the portable set is drawable, rather than a
language-level promise that any string "just works" everywhere.

## RTL — genuinely does not exist, and deserves real skepticism

Grepped for right-to-left, bidi, or reordering logic across `packages/`,
`docs/`, `editors/`: zero hits. It should be treated with real
skepticism, not added as a checkbox feature:

- Every one of these nine machines' native text hardware is a fixed
  character-cell grid addressed by (row, column) with no direction
  concept at the hardware level — `text.print(cell, s)` writes bytes
  starting at a cell address and incrementing. A screen has no more
  concept of "reading direction" than a 2D array does.
- **True RTL script support is not one flag.** It requires bidi
  algorithm–level logical-to-visual reordering (Arabic/Hebrew joining
  forms, mirrored punctuation) — a genuinely heavy run-time or
  compile-time text-shaping problem, and these are 8-bit machines with,
  in the best case, a few KB of RAM and a handful of spare program
  bytes. A full Unicode bidi implementation is not a realistic ask for a
  PET or an unexpanded VIC-20, and pretending otherwise would violate
  this project's core rule about not abstracting away what a program
  can't actually afford.
- What **is** honestly achievable, and should be scoped separately from
  "RTL support": a `direction: 'ltr' | 'rtl'` catalog-level or per-string
  flag that reverses the *cell write order* for an already-shaped,
  already-correctly-ordered string a translator supplies pre-reordered —
  mirroring how retro-scene RTL hacks are actually done today: the
  translator does the Arabic/Hebrew shaping by hand or with an external
  tool, and 8BitScript just writes the resulting glyph sequence
  back-to-front on screen. **PROPOSED**, and it should be documented
  explicitly as "reverse cell order for pre-shaped text," never as "RTL
  script support," so nobody mistakes it for real bidi/shaping.
- A script that needs genuinely new glyphs (Arabic joining forms,
  Hebrew) hits the exact same custom-character-set wall as above — RTL
  and non-Latin character sets are the same underlying hardware problem
  wearing two names, not two separate features.

## A YAML/TOML proposal that keeps the current compile-time contract

Three guarantees are worth preserving, because they're real, tested
value (`packages/compiler/test/i18n-catalog.test.mjs`,
`packages/i18n/README.md`):

1. Schema parity across locales (same keys).
2. Placeholder parity (`{name}`) across locales, same set, checked at
   build time, not at runtime failure.
3. Everything folds to a compile-time literal — no catalog lookup ships
   in the binary; `i18n.format(...)`'s result and its `.length` are both
   known at compile time.

**PROPOSED** shape — YAML (arguably the better fit of the two: TOML's
flat-table style fights nested namespaces more than YAML's natural
nesting does):

```yaml
# src/i18n/en.yaml
game:
  name: "2048"
  score: "SCORE"
  game_over: "GAME OVER"
prompt:
  start: "PRESS {control}"
  start_either: "PRESS {control} OR {other}"
```

```yaml
# src/i18n/de.yaml
game:
  name: "2048"
  score: "PUNKTE"
  game_over: "SPIEL VORBEI"
prompt:
  start: "{control} DRÜCKEN"
  start_either: "{control} ODER {other}"
```

What this changes in the compiler, concretely: `parseCatalogFile`
(`index.mjs:379-384`) currently tokenizes/parses catalog files with the
8BS lexer/parser. A YAML front end would replace only this one function
with a YAML parser call producing the same
`{ namespaces: Map<string, Map<string, {value, placeholders, start, length, file}>> }`
shape `catalogSchema` already returns — every downstream function
(`compareCatalogSchemas`, `prepareCatalog`, `applyCatalogCharset`,
`emitCatalog`) is untouched, because they already operate on that schema
object, not on the AST directly (`catalogSchema`'s return value is the
actual seam). This is a genuinely small, well-isolated change if the
schema abstraction is respected — the risk is scope creep into
"redesign the whole i18n module" when the real change is one parser
function. Source position (`start`/`length`, used for diagnostics) needs
a YAML parser that reports byte offsets, not just line/column — worth
checking candidate libraries for this before picking one. `emitCatalog`'s
regenerated-merge-as-8BS step can stay exactly as is (it's an internal
artifact, never user-facing) — no reason to also regenerate YAML there.

**Dependency cost**: a YAML (or TOML) parser is a new `dependencies`
entry in `packages/compiler/package.json` — but it only ever runs at
build time, on the developer's machine, never shipped to the 8-bit
target or the web bundle, so it has zero effect on program size or
runtime cost, the two things this project actually measures and
protects. The real cost is supply-chain surface (one more dependency to
audit/update) and parser correctness (YAML has well-known ambiguity
foot-guns — `NO` parsing as boolean `false`, unquoted `1.0` version
strings — a `.8bs` string literal has none of these). **PROPOSED**: if
YAML is chosen, either pick a small, well-audited parser (`js-yaml` is
the de facto standard) and add an explicit style-lint step ("always
quote scalar values") to catalog authoring guidance, or lean toward TOML
specifically because it has no such implicit-typing ambiguity for
strings — worth deciding with an actual spike of both against a real
translator's workflow, not on paper alone.

## Config-shape complaint — a real, scoped answer

Since the actual pain is "locale plumbing is spread across three
places," not the five-line `i18n` block itself: **PROPOSED** consolidate
so a `release` entry's `locale` and a target's own default stay exactly
as they are today (they're legitimately a build-matrix concern, not an
i18n concern), but give the `i18n` block itself a `format` field
(`i18n: { format: 'yaml', catalog: 'src/i18n', locales: [...] }`) so the
catalog format is one declared thing, not inferred from file extension
alone — keeps `8bs check`/the language server's "what parser do I run"
question answerable without a filesystem probe.

## Open questions before implementation

- Which parser library, and does it report byte offsets for diagnostics
  (needed to keep `CATALOG_SCHEMA`/`CATALOG_PLACEHOLDER` errors pointing
  at the right line/column in a translator's file).
- Does a mixed project (some catalogs still `.8bs`, a migration period)
  need to be supported, or is this a hard cutover? The
  `discoverCatalogLocales`/`isCatalogFile` glob-by-extension logic would
  need a real answer either way.
- Whether `direction: 'rtl'` (pre-shaped-text cell-reversal, per above)
  is worth building at all before a real target audience asks for it —
  it's a small, honest feature once scoped correctly, but scoping it
  wrong (implying real bidi/shaping) would be a documentation and
  expectation-setting risk more than an engineering one.
- Whether any machine's video chip actually supports a redefinable
  charset cheaply enough to be worth exposing as a `video.customGlyphs`
  capability fact — this needs real per-machine verification, the same
  "verify against primary sources" discipline `docs/project/machines/
  *.md` already holds itself to, not assumed from general 6502-era
  knowledge.
