# Commander X16

[x16emu](https://github.com/X16Community/x16-emulator) is the reference
emulator for the Commander X16 — `8bs build --target cx16` links against
llvm-mos's `cx16` platform (see [LLVM-MOS](llvm-mos.md)), which shares the
C64's KERNAL jump table and BASIC memory layout closely enough that both
targets' `.prg` files load the same way.

There's no packaged build this project trusts, on any platform — an AUR
`x16-emulator` package exists, but it may be outdated or broken, and a
package can drift out of sync with the ROM. That pairing is the crux: the
emulator needs a **matching ROM** (KERNAL/BASIC), built from the same point
in time, per upstream's own notes. So both are built from the official
upstream repositories together:

- emulator: <https://github.com/X16Community/x16-emulator.git>
- ROM: <https://github.com/X16Community/x16-rom.git>

## Automated setup

```bash
8bs setup cx16
```

On macOS (tested on Apple Silicon) and Arch/Manjaro Linux, this does the
whole thing:

1. Checks `mos-cx16-clang` is on `LLVM_MOS_HOME` (see [LLVM-MOS](llvm-mos.md) —
   `8bs setup` doesn't install the compiler toolchain itself).
2. **macOS:** checks the Apple Command Line Tools with `xcode-select -p` and
   offers `xcode-select --install` only if they're absent; then requires
   Homebrew (found via `PATH`, never a hardcoded `/opt/homebrew`) and
   installs the build dependencies `git cmake python pkgconf sdl2 cc65 lzsa`
   with `brew install` if any are missing — asks first. If `brew` itself is
   missing it says so and points at <https://brew.sh>; it never runs the
   Homebrew bootstrap script for you.
   **Linux:** installs `base-devel cmake git python zlib sdl2-compat` with
   `pacman` if missing (asks first), and checks `cc65` and `lzsa` are on
   `PATH` — they're AUR-only, so it tells you `pamac build cc65 lzsa` rather
   than picking an AUR helper for you.
3. Clones (or fast-forwards) both upstream repositories into a cache
   directory — `~/.cache/8bitscript/setup/` (or `$XDG_CACHE_HOME`), never
   `~/Development` or your current directory — and runs `make` in each, as
   your normal user. The emulator's `make` delegates to CMake and produces
   `build/x16emu` and `build/makecart`; the ROM's produces `build/x16/rom.bin`.
   Compiler and linker warnings (AppleClang's `ld: warning: reducing
   alignment of section`, pages of ca65/ld65 notices from the ROM) are
   expected and not failures — only a non-zero exit or a missing artifact is.
4. **Validates the pair before installing anything:** boots the freshly
   built emulator against the freshly built ROM headlessly
   (`x16emu -rom build/x16/rom.bin -testbench`, which boots to the KERNAL's
   `RDY` and exits without opening a window) and reads `-version`.
5. Installs into `/opt/commander-x16/` — `x16emu`, `makecart`, `rom.bin` —
   with `sudo` only for those `mkdir`/`install` steps, and only files whose
   contents actually changed.
6. Puts `x16emu` and `makecart` on `PATH` in `/usr/local/bin`, using the
   platform's launcher strategy (see [Why macOS needs a wrapper](#why-macos-needs-a-wrapper)),
   and warns if `/usr/local/bin` isn't on your `PATH`.
7. Verifies the result the way you'll use it: `x16emu -version` and a
   headless `x16emu -testbench` boot *through the installed launcher*.

It's safe to re-run. A complete installation is recognised up front and
skipped — no Homebrew, no clone, no build, no `sudo` — straight to the
launcher check and verification. If `/opt/commander-x16` is incomplete
(say, the ROM is missing), the emulator+ROM pair is rebuilt *together* so
they still match. An existing `/usr/local/bin/x16emu` that 8bs didn't
install is inspected, explained, and only replaced after you confirm.

Two flags:

```bash
8bs setup cx16 --repair   # same idempotent run; what `8bs doctor` suggests for a broken launcher
8bs setup cx16 --update   # force a fresh pull + build + install of the emulator+ROM pair
```

`--repair` exists for readability — a plain run already repairs a broken
launcher without rebuilding anything.

Once it finishes, confirm with `8bs doctor` — see [Doctor](#doctor) below.

## Why macOS needs a wrapper

This is the one platform-specific trap `8bs setup cx16` exists to absorb,
and it's a real, tested failure.

`x16emu` locates its default `rom.bin` relative to the path it was
**invoked through**, not the path of the real binary. On Linux (Manjaro,
tested) the obvious layout works:

```bash
sudo ln -sf /opt/commander-x16/x16emu /usr/local/bin/x16emu   # Linux: fine
```

On macOS (Apple Silicon, tested) the exact same symlink is broken. Running
`x16emu` from anywhere fails with:

```text
Cannot open /usr/local/bin/rom.bin!
```

because the emulator looked beside the *symlink* — `/usr/local/bin/rom.bin` —
instead of beside the real binary in `/opt/commander-x16/`. The fix is a
launcher script that passes the ROM explicitly:

```sh
#!/bin/sh
exec /opt/commander-x16/x16emu -rom /opt/commander-x16/rom.bin "$@"
```

installed as `/usr/local/bin/x16emu` (mode 755). `"$@"` comes last, so
everything `8bs run cx16` passes (`-prg <file> -run`) still reaches the
emulator after the explicit ROM. `makecart` doesn't read a ROM and stays a
plain symlink on both platforms.

Two things about this are worth knowing even if you never touch it by hand:

- `x16emu -version` does **not** load the ROM (it succeeds even with
  `-rom /nonexistent`), so it can't detect this layout. `8bs doctor`
  inspects the launcher itself and boots the emulator headlessly instead.
- The strategy is explicit per platform in `packages/cli/src/setup/cx16.mjs`
  (`CX16_PLATFORMS`): wrapper on macOS, symlink on Linux. Linux is
  deliberately *not* given the wrapper — its symlink works, and a
  behaviour that only one platform needs shouldn't be hidden inside both.

## Doctor

`8bs doctor` reports Commander X16 as six checks, not one — `command -v
x16emu` succeeding proves almost nothing here (the broken symlink layout
above passes it):

```text
  ok  mos-cx16-clang               clang 19.0.0
  ...
  ok  x16emu (Commander X16)       /usr/local/bin/x16emu
  ok  Commander X16 ROM            /opt/commander-x16/rom.bin
  ok  Commander X16 launcher       wrapper, -rom /opt/commander-x16/rom.bin
  ok  x16emu version               Release 50
  ok  Commander X16 boot           boots to BASIC (headless -testbench)
  ok  Commander X16                ready
```

- **x16emu** — the launcher found on `PATH`, shown as its path.
- **Commander X16 ROM** — `/opt/commander-x16/rom.bin` is a regular,
  readable, non-empty file. (An install this project didn't make — an
  official release zip, say — keeps `rom.bin` beside the real binary;
  that's accepted and labelled as not 8bs-managed.) If the emulator is
  present but the ROM isn't:

  ```text
  FAIL  Commander X16 ROM            not found
        emulator installed but ROM is missing
        run: 8bs setup cx16
  ```

- **Commander X16 launcher** — on macOS, a direct symlink into
  `/opt/commander-x16` is reported specifically:

  ```text
  FAIL  Commander X16 launcher       x16emu is installed as a direct symlink and cannot locate rom.bin.
        run: 8bs setup cx16 --repair
  ```

- **x16emu version** — `x16emu -version` → `Release NN`. Any release
  number passes; nothing is pinned to 50.
- **Commander X16 boot** — `x16emu -testbench` through the launcher, the
  only probe that actually loads the ROM the way `8bs run cx16` will.
- **Commander X16** — `ready` only when the compiler, emulator, ROM,
  launcher, version, and boot all pass.

## Manual reference — macOS

What `8bs setup cx16` automates, step by step, as verified on Apple Silicon
(the build produced `Commander X16 Emulator r50 (next), 77f2bab3` against
a ROM built at `PRERELEASE_VERSION=50` — the installer builds whatever
upstream currently is, not that release specifically).

```bash
# 1. Apple Command Line Tools (skip if `xcode-select -p` already succeeds)
xcode-select --install

# 2. Build dependencies
brew install \
  git \
  cmake \
  python \
  pkgconf \
  sdl2 \
  cc65 \
  lzsa

# 3. Emulator
git clone https://github.com/X16Community/x16-emulator.git
cd x16-emulator
make            # → build/x16emu, build/makecart
./build/x16emu -h
cd ..

# 4. Matching ROM
git clone https://github.com/X16Community/x16-rom.git
cd x16-rom
make            # → build/x16/rom.bin (many ca65/ld65 warnings are normal)
cd ..

# 5. Test the pair before installing
x16-emulator/build/x16emu -rom x16-rom/build/x16/rom.bin

# 6. Install
sudo mkdir -p /opt/commander-x16
sudo install -m755 x16-emulator/build/x16emu   /opt/commander-x16/x16emu
sudo install -m755 x16-emulator/build/makecart /opt/commander-x16/makecart
sudo install -m644 x16-rom/build/x16/rom.bin   /opt/commander-x16/rom.bin

# 7. Launchers — NOT `ln -s` for x16emu on macOS (see above)
sudo mkdir -p /usr/local/bin
sudo rm -f /usr/local/bin/x16emu
cat <<'EOS' | sudo tee /usr/local/bin/x16emu >/dev/null
#!/bin/sh
exec /opt/commander-x16/x16emu -rom /opt/commander-x16/rom.bin "$@"
EOS
sudo chmod 755 /usr/local/bin/x16emu
sudo ln -sf /opt/commander-x16/makecart /usr/local/bin/makecart

# 8. Verify
cd ~ && x16emu -version && x16emu
```

Without `pkgconf`, CMake prints `pkg-config missing. Skipping FluidSynth
auto-detection.` — harmless (FluidSynth is optional), but installing it
lets dependency detection work normally.

## Manual reference — Arch / Manjaro

```bash
sudo pacman -S --needed base-devel cmake git python zlib sdl2-compat
pamac build cc65 lzsa        # AUR
command -v cc65 lzsa
```

Then steps 3–6 above are identical. For the launchers, Linux uses plain
symlinks — the tested Manjaro install locates `rom.bin` correctly through
one:

```bash
sudo ln -sf /opt/commander-x16/x16emu   /usr/local/bin/x16emu
sudo ln -sf /opt/commander-x16/makecart /usr/local/bin/makecart
```

## Debian / Ubuntu

Not automated. The same source-build steps apply with apt's package names
(`build-essential cmake git python3 zlib1g-dev libsdl2-dev cc65`); `lzsa`
isn't packaged for Debian and would need its own source build from
[emmanuel-marty/lzsa](https://github.com/emmanuel-marty/lzsa). Whether a
symlink or a wrapper is needed for `x16emu` on Debian hasn't been tested —
if `x16emu` fails with `Cannot open /usr/local/bin/rom.bin!`, use the
macOS wrapper above.

## Updating later

```bash
8bs setup cx16 --update
```

pulls both repositories, rebuilds, validates the new pair, and reinstalls
only the files that changed. Keep the emulator and ROM updated together —
an emulator built against one revision paired with a ROM built against
another is exactly the mismatch this page exists to avoid.

## Run

```bash
8bs run cx16
```

`8bs run` passes the built `.prg` as `-prg <file> -run`, confirmed against
the X16Community/x16-emulator README. There's no NTSC/PAL split to pick —
the X16 is a single fixed hardware spec, not a family of vintage machines
with region-dependent crystals (see the comment on `FRAME_SYNC.cx16` in
`packages/backend-6502` for what that means for frame timing).

Two things about the picture are the X16, not a bug. The boot banner is
gone by the time a program starts: LLVM-MOS's start-up code switches the
KERNAL into ISO mode (CHR$(15)) before `main()`, and the KERNAL clears the
screen to do it — so a program that draws nothing shows a blank blue text
screen, which is what `examples/borders` looked like before its X16 variant
drew anything. And VERA's border colour has nowhere to show by default —
the active display area fills the whole 640×480 output — so
`@8bitscript/cx16` insets that area by 16 pixels on every side, and that
ring is the border you see. Both are explained in the package's
`src/index.8bs`; the machine's wider set of oddities — banked memory,
VERA's indirect ports and write-only overlays, sprite budgets, the KERNAL
API contract, emulator versus hardware — is collected in
`packages/cx16/AGENTS.md`.
