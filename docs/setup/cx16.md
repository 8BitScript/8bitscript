# Commander X16

[x16emu](https://github.com/X16Community/x16-emulator) is the reference
emulator for the Commander X16 — `8bs build --target cx16` links against
llvm-mos's `cx16` platform (see [LLVM-MOS](llvm-mos.md)), which shares the
C64's KERNAL jump table and BASIC memory layout closely enough that both
targets' `.prg` files load the same way.

There's no macOS or Linux package this project trusts — an AUR
`x16-emulator` package exists, but it may be outdated or broken, and a
source build produces the emulator binary only. Either way you also need a
**matching ROM** (KERNAL/BASIC) alongside it — the same pairing requirement
[VICE](vice.md) and [atari800](atari8.md) have with their own ROMs. The
official release zips on
[GitHub Releases](https://github.com/X16Community/x16-emulator/releases)
bundle a matching `rom.bin`; a source build does not, so the guide below
builds one from [x16-rom](https://github.com/X16Community/x16-rom) to match.

## Arch / Manjaro — build from source

### 1. Install build dependencies

```bash
sudo pacman -S --needed \
  base-devel \
  cmake \
  git \
  python \
  zlib \
  sdl2-compat
```

The X16 ROM also needs `cc65` and `lzsa` (both in the AUR):

```bash
pamac build cc65 lzsa
```

Verify both landed on `PATH`:

```bash
command -v cc65
command -v lzsa
```

### 2. Build x16-emulator

```bash
git clone https://github.com/X16Community/x16-emulator.git
cd x16-emulator
make
```

The build (CMake underneath) produces `build/x16emu` and `build/makecart` —
not repository-root binaries, unlike older versions of this guide's advice.
Verify it runs:

```bash
./build/x16emu -h
```

### 3. Build a matching ROM

The emulator needs a ROM built from the same point in time — an older or
newer `rom.bin` may not work against a given emulator build, per upstream's
own notes.

```bash
cd ..
git clone https://github.com/X16Community/x16-rom.git
cd x16-rom
make
```

This produces `build/x16/rom.bin`.

### 4. Test the pair

From the `x16-rom` directory:

```bash
../x16-emulator/build/x16emu -rom build/x16/rom.bin
```

The Commander X16 BASIC screen should appear.

### 5. Install system-wide

```bash
sudo mkdir -p /opt/commander-x16
sudo install -m755 ../x16-emulator/build/x16emu /opt/commander-x16/x16emu
sudo install -m755 ../x16-emulator/build/makecart /opt/commander-x16/makecart
sudo install -m644 build/x16/rom.bin /opt/commander-x16/rom.bin
sudo ln -sf /opt/commander-x16/x16emu /usr/local/bin/x16emu
sudo ln -sf /opt/commander-x16/makecart /usr/local/bin/makecart
```

`x16emu` looks for a ROM alongside itself by default, so once it's a symlink
into `/opt/commander-x16/` (where `rom.bin` also lives), running `x16emu`
from anywhere picks it up without `-rom`. Verify:

```bash
command -v x16emu
x16emu -version
```

`8bs doctor` checks the same two things: `x16emu` on `PATH`, then
`x16emu -version` for a version line to report.

### Updating later

```bash
cd x16-emulator && git pull && make && cd ..
cd x16-rom && git pull && make && cd ..
sudo install -m755 x16-emulator/build/x16emu /opt/commander-x16/x16emu
sudo install -m755 x16-emulator/build/makecart /opt/commander-x16/makecart
sudo install -m644 x16-rom/build/x16/rom.bin /opt/commander-x16/rom.bin
```

Keep the emulator and ROM updated together — an emulator built against one
revision paired with a ROM built against another is exactly the mismatch
this guide exists to avoid.

## macOS

Homebrew has the same build dependencies (`brew install cmake sdl2 cc65
lzsa`), but this project hasn't independently verified the build on macOS —
the ROM-pairing requirement above still applies either way. The simplest
path on macOS is likely the official release zip, which already bundles a
matching `rom.bin`.

## Debian / Ubuntu

No AUR-equivalent search was done here — the same source-build steps apply
with apt's package names (`build-essential cmake git python3 zlib1g-dev
libsdl2-dev cc65`); `lzsa` isn't packaged for Debian and would need its own
source build from [emmanuel-marty/lzsa](https://github.com/emmanuel-marty/lzsa).

## Run

```bash
8bs run cx16
```

`8bs run` passes the built `.prg` as `-prg <file> -run`, confirmed against
the X16Community/x16-emulator README. There's no NTSC/PAL split to pick —
the X16 is a single fixed hardware spec, not a family of vintage machines
with region-dependent crystals (see the comment on `FRAME_SYNC.cx16` in
`packages/backend-6502` for what that means for frame timing).
